# С чего начать в Chronos

Сначала прочитай этот файл **из корня текущего checkout**. Выбирай по запрошенному результату. Обычно достаточно роутера и одного профильного скилла. Третий открывай, когда нужен отдельный шаг приёмки или выпуска. Ссылки на соседние скиллы служат справкой. В установленной копии относительные ссылки разрешай от одноимённого SKILL.md в репозитории.

Для ожидаемого скилла сначала проверь `chronos/skills/<скилл>/SKILL.md` текущего checkout. Если файла ещё нет, используй команду `git show` из его строки. Когда доступна только локальная ветка, убери префикс `origin/`. Если ни в одном ref файла пока нет, укажи это и используй [chronos-feature](../chronos-feature/SKILL.md) для разработки. Проверь доступность инструментов в текущей версии. Для замеров есть [методика стенда](../../scripts/bench/README.md). Для вопроса об устройстве форка достаточно [карты интеграций](../../README.md). Для ревью самих скиллов пройди [валидацию и синхронизацию](../../README.md#скиллы).

## Общие правила

- На слабом ПК и серверах в первую очередь проверяй стабильность, время отклика и память. Новые возможности выключены по умолчанию или загружаются при первом обращении. Модель и глубину рассуждений пользователя сохраняй.
- Сохраняй байты [модулей Olympus](../../../apps/web/src/chronos/olympus/features), минимальные стыки апстрима с `// chronos:` и глоссарий Olympus.
- Зависимости, сборку монорепо и полный typecheck запускай в CI. Локально используй существующие зависимости и точечные проверки по очереди. Если нужен интерфейс, выбери проверенный экземпляр Chronos или [подходящий режим стенда](../../scripts/bench/README.md).
- Всегда нужно явное согласие пользователя на запись в устройства и прошивку, установку или любые изменения на gildra и debian-151, изменения установленного T3/Olympus и `~/.t3`, удаление данных пользователя, платные прогоны API, force-push и удаление тегов или релизов. Метрики серверов можно читать. Береги службы на 4517–4524 и чужие процессы. Секреты запрашивай только через `request_secret`. В публичный репозиторий попадают только обезличенные данные.
- Для задач на изменение Chronos постоянно разрешён полный цикл без дополнительных вопросов: сессии-исполнители → проверка → слияние в `main` → push → тег и релиз `chronos-v*`. Явное ограничение задачи (только отчёт, план или ветка) определяет, на каком шаге остановиться. Исполнители используют отдельные ветки и worktree, `codex` / `gpt-6.2-astra`, `reasoningEffort: "xhigh"`, и ждут CI в шелле. Интеграцию и выпуск ведёт оркестратор.
- До продвижения `main` нужны зелёные **Chronos checks**, полный ручной `chronos-desktop` на точном SHA кандидата, `chronos-smoke` 14/14 по его `desktop_run_id` с `require_services=true` и `require_provider=true` и `chronos-perf.yml` для пары прежний main / кандидат. Пока шлюза нет в `main`, используй workflow из `perf/guard`. Без зелёного результата для этой пары слияние и выпуск ждут.
- В ежедневной синхронизации дополнительно нужны паритет и разбор регрессий.
