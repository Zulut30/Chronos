# План: встроить сервисы Olympus, догнать свежий T3, перейти с Olympus на Chronos

Состояние на 2026-11-25: `main` = перенос Olympus один в один на T3 `0.1.10-nightly.20261116.4774`,
релиз `chronos-v0.1.10-nightly.20261116.4774.chronos.4` опубликован. Olympus (установленный T3 с
патчами) — эталон, его не трогаем до этапа 4.

Порядок: **0 → (1 ∥ 3) → 2 → 4.** Этапы 1 и 3 затрагивают разные файлы и идут параллельно.

## Этап 0. Эталон и smoke-проверки (основа для всех этапов)

Сейчас Chronos 4774 совпадает с Olympus, поэтому его поведение можно зафиксировать как эталон.

1. Скрипт `chronos/scripts/smoke/` (CDP): запуск Chronos с `--remote-debugging-port`, для каждого модуля
   Olympus — признак работы (глобальные объекты `__oly*`, ключевые элементы DOM, отсутствие ошибок
   консоли), обход экранов (главный, треды, настройки и страницы Olympus, статистика, доска задач,
   студия), скриншоты. Только демо-данные: тестовый проект, без личных проектов, задач и ключей.
2. Прогон на текущей сборке — эталонные скриншоты и отчёт в `chronos/parity/baseline/`.
3. CI: job на `windows-latest` ставит собранный установщик молча, запускает smoke без входа и агентов.
4. Ворота для `main`: `chronos-checks` + `chronos-parity` + smoke.

Готово, когда smoke зелёный на 4774 и ловит заведомую поломку (проверить на подмене модуля).

1. `chronos-upstream.yml` раз в сутки: новый nightly → ветка `upstream-sync/<дата>` → попытка слияния.

3. Слияние и релиз — по решению пользователя: каждый по слову или постоянное разрешение

## Этап 3. Встроить сервисы Olympus в Chronos (параллельно с этапом 1)

Факты: 8 сервисов. tasks (4518), skills-manager (4517), files (4519), integrations (4522), olympus-hub
(4524) и openrouter (stdio MCP) — Node без npm-зависимостей; studio (4520) — 42 МБ, собранный редактор
Excalidraw и WordPress Playground; mcp-manager (4523) — Python-воркер (sqlite3, SSH); hub — Python-скрипты
и Rust-ланчер (Windows). Путь `~/.t3` зашит (tasks, skills, studio, mcp читают `statev2.sqlite`).
CORS сервисов уже пускает `t3code://app`. Сейчас их запускают `.vbs` из «Автозагрузки».

Схема — sidecar-процессы, код сервисов как есть:
1. Код — в `chronos/services/<имя>` из актуальных версий (по описи `inventory/services`); правка только
   параметризации путей (база данных из переменной окружения; по умолчанию `~/.chronos`, после
   перехода — `~/.t3`).
2. Упаковка: `extraResources` установщика; запуск из Electron main (`apps/desktop/src/chronos/services/`)
   через `ELECTRON_RUN_AS_NODE` — ставить Node не нужно. Перед запуском — проверка порта: если там уже
   отвечает сервис Olympus, второй не поднимаем. Остановка при выходе, логи в `~/.chronos/logs`.
3. Python: чтение `statev2.sqlite` — через `node:sqlite` вместо Python; mcp-manager — системный Python
   (без него раздел показывает понятное сообщение) или перенос воркера на Node — решение пользователя.
   Rust-ланчер хаба заменить запуском через Node (кроссплатформенно).
4. Ключи API: Windows — `HKCU\Environment` как сейчас; macOS — файл окружения в `~/.chronos`.
5. MCP-регистрации агентов (oly-tasks, oly-skills, oly-web, t3-studio, openrouter): до перехода не
   трогать регистрации Olympus; при переходе переключить на копии Chronos.
6. Лицензии: Excalidraw — MIT; WordPress Playground — GPL: поставлять как отдельную программу с текстом
   лицензии и ссылкой на исходники; дополнить `NOTICE.md`.
7. Проверка: smoke всех разделов (задачи, студия, скиллы, файлы, ключи, MCP) на чистом CI без Olympus.

Цена: установщик примерно +45 МБ.

## Этап 4. Переход с Olympus на Chronos (после этапов 1 и 3)

Решение по умолчанию: Chronos открывает данные пользователя на месте (`~/.t3`), а не копию —
сохраняются треды, проекты, настройки, привязка телефона и окружение T3 Connect. Olympus и Chronos
после этого одновременно не запускать (одна база и один `environment-id`).

1. Закрыть Olympus. Бэкап `~/.t3/userdata` (около 2,6 ГБ: `statev2.sqlite` с WAL, настройки, темы,
   secrets) и профиля Electron Olympus (`%APPDATA%\t3code-v2`).
2. Перенести `localStorage` Olympus (состояние модулей: режимы ответа, псевдонимы, клиент студии и др.)
   в профиль Chronos.
3. Направить Chronos на `~/.t3` (явная настройка или `CHRONOS_HOME`), убрать тестовые данные.
4. Первый запуск — миграции БД на новую схему (для Olympus 4774 необратимо; откат = бэкап).
5. Сервисы: выключить `.vbs` Olympus в «Автозагрузке», сервисы запускает Chronos; MCP-регистрации
   переключить на Chronos.
6. Вход в аккаунт T3 Connect по коду из письма.
7. Ярлыки и панель задач → Chronos. Olympus оставить установленным для отката.
8. MacBook — тем же порядком после Windows.

Откат: закрыть Chronos → восстановить бэкап → включить `.vbs` → запустить Olympus.

## Решения пользователя

1. Ежедневные релизы: каждый по слову или постоянное разрешение при зелёных CI и smoke.
2. Переход: данные на месте (`~/.t3`, рекомендуется) или копия (отдельное окружение, повторная привязка телефона).
3. mcp-manager: системный Python или перенос воркера на Node.
4. WordPress Playground (GPL) в составе установщика.
