# Ресурсы Chronos 5209 при параллельной работе агентов

Ветка `perf/resources-2` ответвлена от `fc32d3f23a`. На Windows основные изменения уменьшают постоянные расходы одного экземпляра Chronos. Количество агентов свободное. Серверный архив переносит изменения форка на управляемый SSH-сервер при выборе источника.

Все числа памяти ниже в МиБ. **Private** — private commit. Сумма working set (WS) нескольких процессов включает общие страницы несколько раз. По разнице WS нельзя вычислить, сколько новых агентов поместится в 32 ГБ. Медианы получены из трёх запусков каждой конфигурации на Windows 11 x64, Ryzen 9 5950X, 32 ГБ. Стенды использовали временные каталоги, локальные моки и свободные порты. Рабочий профиль, открытое окно и SSH-хосты в экспериментах не участвовали.

## 1. Семь сервисов Olympus в одном хосте

Десктоп запускает хост по первому свободному порту. У каждого из семи HTTP-сервисов отдельный Node Worker, контекст V8, порт и журнал. Проверка владельца порта, повтор с задержкой и повторная проверка перед занятием порта остались в десктопе. Относительные пути API разрешаются от прежнего рабочего каталога сервиса. Потеря IPC с десктопом завершает хост. OpenRouter stdio запускается клиентом по его собственному stdin/stdout.

| Все семь сервисов | Отдельные процессы | Общий хост |
|---|---:|---:|
| Процессы сервиса | 7 | 1 |
| Суммарный WS | 398,63 | 132,75 |
| Private | 180,20 | 176,05 |
| CPU за 70 запросов health, с | 0,047 | 0,047 |

Получено **−265,88 МиБ суммарного WS и −4,16 МиБ private**. Диапазоны private составили 179,90–181,24 и 173,34–176,21. У каждого HTTP-модуля остаётся свой JS heap. Измерение CPU короткое, в отдельных сериях значение попадало в ноль из-за дискретности счётчика.

В тесте занятый порт заставляет `tasks-service` вызвать реальный `process.exit(1)`. В том же хосте отвечает Studio, после освобождения порта поднимается новый tasks Worker. Smoke проходит маршруты досок, файлов, проектов, шаблонов, MCP и проверяет авторизацию хаба на изолированных портах. У всех воркеров общий отказ при аварии нативного процесса или исчерпании памяти процесса целиком. Тогда менеджер восстанавливает доступные службы. [Изоляция Node Worker](https://nodejs.org/api/worker_threads.html)

## 2. SQLite, WAL и история

Повторены исходные Windows-артефакты quick-wins. SHA-256 `server.asar` базы `ca2490826a` — `b1a0d38a3016e8dba38cac918c529f320f9af22ed674a2cf678453eadd76dcad`, кандидата `f72bab89c6` — `3a55a51fc2b1f4347fe2f4e8a7d22d19c33905f48d491c24792f7f8e28b94d30`. Порядок пар AB/BA/AB. В каждом прогоне 16 ACP-агентов × 80 абзацев, до и после нагрузки — короткий read-only снимок. Получены 7680 маркеров и 96 полных ответов. Результат каждого ответа проверен по контрольному тексту. [Исходное сравнение](perf-quick-wins.md)

| Рост за интервал, база → quick-wins | Пара 1 | Пара 2 | Пара 3 |
|---|---:|---:|---:|
| SQLite + WAL + SHM, МиБ | 21,71 → 12,95 | 33,28 → 38,49 | 15,99 → 19,43 |
| Только WAL, МиБ | 15,24 → 6,20 | 27,42 → 32,19 | 8,84 → 12,81 |
| Занятые страницы, МиБ | 6,43 → 6,71 | 5,79 → 6,23 | 7,11 → 6,59 |
| Строки `orchestration_events` | 843 → 893 | 800 → 835 | 924 → 878 |
| JSON событий, МиБ | 4,22 → 4,47 | 3,66 → 4,08 | 4,71 → 4,32 |

В исходной серии сумма файлов выросла с 6,84 до 16,01. В повторе медианы поменялись местами — **21,71 → 19,43**. Медиана занятых страниц составила **6,43 → 6,59**, записанных событий **843 → 878**. Сумма полезных данных между запусками меняется при объединении стриминговых обновлений, итоговые ответы совпадают. Устойчивого двукратного роста логической истории серия не показывает. На этом стенде работает ACP, Claude не запускается. Выгрузка простаивающего Claude не объясняет исходный показатель. Продолжительная работа реального Claude и состав пользовательской БД на 3,5 ГБ этой серией не измерены.

**Изменение дефолта.** Лимит повторно используемого WAL снижен со 128 до 32 МиБ. На удерживаемом читателем снимке 20 транзакций обновили одни и те же 1024 строки. Пик WAL в обеих конфигурациях 80,47. После выхода читателя, PASSIVE checkpoint и следующей записи осталось **80,47 → 32,00 МиБ** во всех трёх парах. Проверены видимость старого снимка, сумма версий и `integrity_check`. Медианы CPU 843 → 657 мс, длительности серии 1652 → 1978 мс, p95 commit 63 → 58 мс. По времени есть разброс вплоть до p95 401 мс. Доказанный эффект здесь — 48,47 МиБ диска после пика. Удерживаемый WAL и основной файл могут превышать 32 МиБ. [Checkpoint и повторное использование WAL](https://www.sqlite.org/wal.html)

| Политика Chronos | Выбранное поведение |
|---|---|
| Checkpoint | Отдельный worker запускает PASSIVE после 1000 незаписанных в основной файл кадров. При паузе в записи он догоняет хвост через 100 мс. Подключение писателя имеет резервный `wal_autocheckpoint=10000` при работающем worker. Оставлены штатные пороги. Принудительный TRUNCATE при активных агентах не добавлен. |
| История использования | Настройка `usageHistoryRetentionDays` по умолчанию 92 дня, допускает положительное целое или `unlimited`. Она ограничивает обработку старых записей usage и их кэш. История чатов имеет отдельный жизненный цикл. |
| События и снимки | Штатное уплотнение каждые 6 часов удаляет покрытые проекциями события за сохранённой границей, оставляет хвост не менее суток, последнюю запись потока и необходимые квитанции. Устаревший клиент восстанавливается из снимка. Дополнительного удаления проекций или снимков по возрасту нет. |
| Свободные страницы | Новые БД используют incremental auto-vacuum. Штатный проход возвращает до 1024 свободных страниц в минуту. Для старой БД переход требует полного офлайн VACUUM. Его выполняют отдельно по решению владельца, после проверки свободного места и остановки сервера. |

## 3. Electron, скрытые вкладки и SnapShot

Windows запускает помощники области снимка и accessibility по первому запросу. Запасные процессы для повторной съёмки освобождаются через 60 секунд. Процесс, которому передан текущий захват, исключается из таймера. Глобальное сочетание клавиш обслуживает прежний обработчик.

| Два помощника SnapShot до первого вызова | Было | Стало |
|---|---:|---:|
| Процессы | 2 | 0 |
| WS / private, МиБ | 108,09 / 66,98 | 0 / 0 |
| CPU подготовки, мс | 344 | 0 |
| От запроса до готовности обоих процессов, мс | 0,08 | 192 |

Использованы настоящие упакованные воркеры Electron с подтверждением готовности IPC. Холодная задержка составила 171–295 мс. Тест проверяет истечение таймера, сохранение активного процесса и повторное получение после истечения. Проверка готовности не включает время захвата или распознавания содержимого пользовательского экрана.

В изолированном offscreen-окне Electron отрисованы две локальные webview и список из 180 DOM-элементов, обновляемых 100 кадров. При удалении скрытой вкладки число гостей 2 → 1 и процессов 6 → 5. Медиана для обычных флагов — минус 72,21 МиБ WS и 22,79 МиБ private. Уничтожен тот самый `webContents`, в котором находилось несохранённое поле. В Chronos такой гость также обслуживает скрытые команды агента, запись и PiP. Автовыгрузку загруженных страниц оставили за решением о допустимой потере состояния.

|---|---:|---:|---:|

У всех конфигураций было шесть процессов. Private обычной конфигурации менялся от 259,51 до 332,40 МиБ, с отключённым spare renderer — от 262,61 до 331,03. Для V8 выполнен дополнительный тест на настоящем веб-клиенте quick-wins в Chromium Headless Shell с 16 активными моками. Основное окно уже возвращает `setBackgroundThrottling(true)` перед первым показом. Окна анимации и PiP, а также захват скрытого гостя временно требуют кадров. ## 4. PowerShell, консоли и агентские CLI

При активных агентах сервер держит один блокировщик сна на машину. Windows-версия из комплекта Chronos теперь вызывает `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED)` в специальном режиме Rust-помощника. Готовность сообщается только после успешного вызова. Помощник читает приватный stdin и завершается при EOF, включая аварийный выход родителя. Он освобождает консоль через `FreeConsole` и сохраняет обычное управление дочерним процессом. Вариант WSL и резервный запуск без комплектного помощника используют прежний путь.

| Блокировщик сна | PowerShell | Нативный помощник |
|---|---:|---:|
| WS / private, МиБ | 92,45 / 76,53 | 9,40 / 1,66 |
| Дочерние conhost | 1 | 0 |
| Готовность, мс | 567 | 65 |
| CPU до измерения, мс | 484 | 0 по медиане, до 62,5 |

На этом ПК запуск отдельного тестового консольного процесса с перенаправленными потоками и `CREATE_NO_WINDOW` дал скрытый conhost во всех трёх попытках. Нативный блокировщик до `FreeConsole` тоже держал один conhost, около 1,25–1,63 МиБ private. После исправления проверены ответ `held`, нормальный выход при закрытии stdin и выход при исчезновении родителя. Заявленная экономия относится к одному активному блокировщику. [Флаги Win32](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags) · [Реализация libuv](https://github.com/libuv/libuv/blob/v1.x/src/win/process.c)

| Владелец консоли | Что можно изменить |
|---|---|
| Терминал Chronos | `NodePtyAdapter` создаёт PTY по запросу терминала. В Windows это ConPTY с собственной геометрией, вводом и сигналами. Закрытие терминальной сессии освобождает оболочку. Подмена PTY общим stdin нарушила бы независимость сессий. [Устройство ConPTY](https://learn.microsoft.com/en-us/windows/console/creating-a-pseudoconsole-session) |
| Транспорт провайдера | Windows-ветка Claude использует `SpawnWorker.spawnPiped` с `windowsHide`. Для команд без интерактивного ввода достаточно перенаправленных потоков. Внутренние PowerShell, PTY, stdio MCP и процессы фоновых команд создаёт запущенный CLI. Опция родительского spawn на эти вызовы не распространяется. |
| Claude Code | Разовые команды можно завершать в foreground. Уже ненужный фоновый shell останавливается адресно через `TaskStop` по идентификатору. Настройки пользователя не менялись. [Справка Claude](https://code.claude.com/docs/en/agent-sdk/typescript#taskstop) |
| Codex | Для неинтерактивной команды подходит `exec_command` с `tty=false`. Повторную оболочку PowerShell внутри уже выбранной оболочки можно убрать из самой команды. Если в конкретном профиле включён `shell_environment_policy.experimental_use_profile`, отключение исключает загрузку пользовательского профиля, с возможным изменением PATH и функций. [Справочник Codex](https://developers.openai.com/codex/config-reference) |

## 5. Собственные архивы CLI для SSH

Ручная сборка `chronos-desktop.yml` выпускает тестовые артефакты под Linux x64, Linux ARM64 и macOS ARM64. Каждый содержит SEA-исполняемый файл, веб-клиент, нативные зависимости и штатный resource monitor. На платформенном раннере разворачивается архив, проверяются версия, service-launcher и HTTP-ответ сервера. При будущем релизе workflow добавляет архивы из проверенной сборки и их SHA-256 в общий файл сумм. macOS x64 исключён вслед за апстримом, где SEA этого таргета падает при старте.

По умолчанию SSH использует официальный архив. Для выбора форка нужно запустить десктоп с `CHRONOS_SSH_CLI_SOURCE=chronos` и переподключить окружение. Возврат к `upstream` или удаление переменной возвращает официальный источник. Это явный откат. Ошибка проверки суммы прерывает установку. Путь архива включает `chronos-v<версия>`, отдельный кэш включает ревизию форка. Сервер сообщает базовую версию T3 5209. Схемы RPC, мобильного подключения и relay не менялись. На внешнем или принадлежащем другому лаунчеру сервере сохраняются правила заимствования. При смене источника своего сервера штатный лаунчер заменяет процесс, поэтому переключение планируют между рабочими сессиями.

Проверка SSH дважды переключает управляемый сервер с одной базовой версией и подтверждает смену PID, затем переиспользование PID при повторном подключении. Отдельная проверка сохраняет более новый сервер при подключении старого клиента. В Linux CI два настоящих архива устанавливаются штатным shell-скриптом с контрольными суммами в пустой HOME. Из каждого исполняются одинаковые изменения проекта. Рабочие gildra и debian-151 не обновлялись, сквозной вход с мобильного устройства или через T3 Connect не проверялся.

На Linux x64 выполнены три пары официальный → Chronos с чередованием порядка. Каждый запуск создал один проект, принял 80 подтверждённых изменений названия и вернул ожидаемую последнюю запись из SQLite. [Нативный тест и все шесть результатов](https://github.com/Zulut30/Chronos/actions/runs/45611343005/job/139197213928)

| 80 изменений проекта, медианы | Официальный CLI | Chronos CLI |
|---|---:|---:|
| Записано в локальный trace, байт | 1 171 117 | 69 766 |
| CPU сервера, мс | 910 | 580 |
| RSS сервера, МиБ | 482,41 | 483,20 |
| Время команд, мс | 528 | 456 |

Архив доставил уже реализованную выборочную запись трейса, в этой операции объём уменьшился на 94%. Измерение относится к проектным командам на CI-раннере. Расход работающих моделей и количество одновременно обслуживаемых агентов на gildra/debian-151 по нему определить нельзя.

## Воспроизведение и решения

- Стенд приложения — `chronos/scripts/bench/run.mjs`. Аргументы описаны в [README](../scripts/bench/README.md). Поля `databaseBefore/After` содержат страницы, размеры трёх файлов и события каждого типа.
- Порты и профиль сервисов — временные. Для серии WS/private установите `ELECTRON_RUN_AS_NODE=1`, `CHRONOS_BENCH_SIDECARS=1` и запустите распакованный `Chronos.exe --test chronos/scripts/smoke/service-host.test.mjs`.
- `node chronos/scripts/bench/windows-helpers.mjs snapshot <распакованный-каталог>` и `inhibitor <путь-к-новому-t3-resource-monitor.exe>` проверяют процессы Windows. `node chronos/scripts/bench/renderer.mjs <распакованный-каталог>` создаёт отдельный профиль и скрытое окно. Варианты V8 для реального клиента задаются через `BENCH_FRAME_TIMES=1` и `BENCH_V8_SIZE=1`.
- `chronos/scripts/bench/sqlite-wal.mjs` выполняется через комплектный Electron в режиме Node. Сценарий Linux находится в `chronos/scripts/bench/ssh-cli.mjs`.
- Решения владельца — когда публиковать архивы и переключать серверы, требуется ли отдельный офлайн-проход для старой пользовательской БД, допустима ли потеря несохранённого состояния скрытых страниц. Дополнительные ограничения параллельности не вводились.
