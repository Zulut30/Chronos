# Параллельные агенты Chronos 5209

## Что сравнивалось

Две Windows x64 сборки из CI. База — [`ca2490826a`](https://github.com/Zulut30/Chronos/actions/runs/45583500133), кандидат — [`f72bab89c6`](https://github.com/Zulut30/Chronos/actions/runs/45597843405). После сборки кандидата изменились только шаг CI для теста мока и отчёт. SHA‑256 `server.asar` у базы — `b1a0d38a3016e8dba38cac918c529f320f9af22ed674a2cf678453eadd76dcad`, у кандидата — `3a55a51fc2b1f4347fe2f4e8a7d22d19c33905f48d491c24792f7f8e28b94d30`. Предварительные прогоны установленного Chronos исключены из таблиц, поскольку его архив отличается от выбранной CI-базы.

Windows 11 Pro 26200, Ryzen 9 5950X, 32 логических процессора, 31,9 ГиБ доступной ОС физической памяти. Драйвер и моки работали под Node 24.19.0. Сервер работал под собственным Electron в режиме Node, UI — в отдельном Chromium Headless Shell из локального пакета Playwright `chromium_headless_shell-1248`. Для каждого прогона создан новый временный профиль. Рабочее окно Chronos, CDP 9333 и установленные сервисы Olympus в измерениях не участвовали.

Каждый агент пишет 80 абзацев с паузой 125 мс. У всех процессов общий старт после синхронизации N детальных WS-подписок и появления первого треда в renderer. Включён обычный режим стриминга по абзацам. Для каждого N приведены три прогона базы и три прогона финального кандидата. Базовые результаты взяты из контрольной серии с чередованием сборок. Финальный артефакт прошёл отдельные три круга 4 → 8 → 16 на том же ПК и с теми же параметрами. До старта подготовлены Git-проект, модели, подписки и DOM. [Команда запуска и описание метрик](../scripts/bench/README.md).

## Контроль условий измерения

Перед расширением списка адресуемых Codex-событий на [`2a3d134446`](https://github.com/Zulut30/Chronos/actions/runs/45594238421) работал тот же код для ACP. В 18 запусках база и эта версия чередовались внутри каждой пары. Порядок менялся между повторами. При коротком ответе медианы CPU сервера (база → ветка) на 4, 8 и 16 агентах составили 17,2 → 21,3%, 26,8 → 27,3%, 46,4 → 49,4%. Медианы p95 доставки составили 529 → 535, 535 → 541, 554 → 569 мс. На четырёх агентах один прогон ветки дал p95 1691 мс при двух остальных 523 и 535 мс. Все ответы прошли проверку, выброс сохранён.

В дополнительной серии на N=16 ответ увеличен вдвое, до 160 чанков на агента. Три цикла с ротацией порядка «база / ветка / ветка с `Info`». В каждой строке медиана трёх измерений. Сверены 23 040 маркеров и 144 полных ответа.

## Изменения

| Участок | Изменение и проверка |
|---|---|
| Общая сессия Codex | Для корневых сообщений, обычных узлов и элементов хода проверяются совпадение runId, threadId и принадлежность корневому треду. Узлы планов, элементы планов и задачи, которые следующий запуск может унаследовать, проходят штатную маршрутизацию. Steer адресуется по запуску. На смене состава подписчиков индекс строится заново. Для событий дочерних тредов, terminal, handoff и наблюдателей без привязки сохранена общая доставка. Проверены реальная очередь одного из двух активных запусков, общий маркер для соседа, закрытие подписки и точное число доставок для 4/8/16 запусков. Сценарии отмены и переноса фоновой работы проверяют штатные тесты менеджера и RunExecutionService. |
| Размер snapshot | WeakMap хранит длину UTF-8 для идентичного объекта после успешного кодирования. Новый snapshot получает новую оценку. JSON-строка не удерживается. Тест считает вызовы кодера на общем и новом объектах и проверяет многобайтовый текст. |
| Доставка committed events | На активный threadId выделяется канал с подсчётом подписок. После commit сервер группирует события по имеющимся каналам с сохранением порядка. Последний подписчик освобождает запись. Replay, high-water и ограничение буфера сохраняют штатный порядок. Тест проверяет смешанную пачку, двух читателей одного канала и повторное открытие. |
| Статистика OpenCode / OpenRouter | Один вызов физического reader на набор instances и временное окно. Обе логические группы получают свои файлы, статусы и идентификаторы источников в прежнем порядке. Интеграционный тест считает вызовы настоящего reader и проверяет суммы по реальным фикстурам и алиасам каталогов. |

### Точный смысл T3CODE_TRACE_MIN_LEVEL

Параметр задаёт Effect `Tracer.MinimumTraceLevel`. Здесь допустимое написание уровня предупреждений — `Warn`. Значение по умолчанию — `Info`. Effect выбирает флаг `sampled` при создании span с учётом уровня, решения родителя и явного `sampled`. В прежнем локальном трассировщике процентного отбора обычных успешных span нет. Порог `Warn` отсекает начатый при `Info` span ещё до того, как операция вернёт ошибку или выдаст предупреждение.

По умолчанию Chronos сохраняет каждую шестнадцатую обычную успешную запись, все ранее записываемые ошибочные выходы и span с логами Warn/Warning, Error или Fatal. Решение применяется только к файлу сервера после завершения span. В штатном пути синхронную работу создают преобразование и сериализация записи. Файловые операции буферизуются с окном 1 с, предусмотрен отдельный синхронный сброс при выходе. OTLP-экспорт и консоль сохраняют свои настройки. Для диагностики с прежней полнотой укажите `T3CODE_TRACE_MIN_LEVEL=Info` перед запуском процесса. Статистика обычных успешных span в диагностике по файлу теперь выборочная.

## Что отложено

| Вариант | Риск и способ безопасной проверки |
|---|---|
| Лимит подробных фоновых подписок RunningThreadKeepAlive | Ввести настраиваемый лимит только для невидимых тредов. Оставлять видимые треды, approvals, вопросы и зависимости родителя. Перед вытеснением сохранить sequence, при открытии немедленно возобновить поток. На двух клиентах проверить reconnect, переключение вкладки в момент commit, медленный ACK и запрос в дочернем треде. Сверить финальные проекции, присутствие карточек и количество повторных соединений. |
| Троттлинг Markdown | Объединять только промежуточные обновления незавершённого блока. Финальный текст и смену треда доставлять сразу. На длинном ответе с таблицами, незакрытым кодом и поиском сравнить время ввода/кадра, выделение, прокрутку и итоговый DOM. Отдельно проверить остановку и ошибку в середине блока. |
| Очередь запуска тяжёлых CLI | Ограничивать холодные старты на provider/instance. Освобождать слот после готовности или ошибки и поддерживать отмену ожидания. Проверить запуск ребёнка ожидающим родителем, отмену до/после spawn, рестарт и зависший CLI. Измерять время ожидания, пик памяти дерева процессов и число завершённых работ отдельно от steady-state. |

## Решение по слиянию

Рекомендую включить семь правок со стендом и регрессионными тестами. Подтверждён самый большой и повторяемый эффект — сокращение объёма локального трейса. Для общего Codex-рантайма тест с N независимыми steer-событиями проверяет N доставок вместо прежних N². Для сканера проверен один вызов reader вместо двух. Размер выигрыша этих двух изменений на живой пользовательской сессии остаётся открытым: ACP-стенд не запускает Codex и не открывает статистику во время нагрузки.

На этом ПК медианы финальной серии на 8 и 16 агентах показывают снижение CPU сервера. В чередующейся короткой серии знак изменения отличался, а на 4 агентах стабильного выигрыша нет. Для планирования ёмкости разумно опираться на проверенную корректность 16 параллельных моков и объём трейсов. Перенос процента ускорения на реальные CLI или Electron потребует отдельных замеров. Для трёх отложенных изменений приведены сценарии проверки выше.
