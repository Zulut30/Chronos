# Бюджет производительности Chronos

[Бюджет](../perf-budget.json) задаёт допустимое ухудшение относительно одновременно измеренного main. Для времени, FPS и файлов также действуют абсолютные границы. Для каждой пары workflow берёт готовые Windows-пакеты по полному SHA, при необходимости штатный Chronos desktop собирает только Windows по неизменяемому SHA. Раннер сверяет SHA из пакета с планом, в том числе когда ветка успела измениться. Ветки, которые содержат workflow, запускают проверку при push. До включения в основную ветку контрольную серию запускает push в perf/guard с маркером `[perf-audit]` в сообщении коммита.

Одна пара занимает одну Windows VM. Три раунда меняют порядок запусков A/B, B/A, A/B. Каждый сценарий получает новый профиль. Шлюз сравнивает медианы. При заданных относительном и абсолютном допусках действует больший из двух. Отсутствующая серия или функциональная ошибка переводит задание в FAIL. Для каждого сценария действует предельное время 8 минут. При таймауте раннер завершает только дерево данного сценария, записывает ошибку и собирает остальные серии. Таблица находится в сводке Actions, исходные замеры и идентификаторы пакетов доступны в артефакте.

| Сценарий | Измерение |
|---|---|
| unused | Пустой десктоп. Если пакет поддерживает управление ПК, предварительно разрешено использование с пустым списком целей и подтверждением каждого действия. Состояние проверяется через штатный IPC. Агент его не вызывает, галерея артефактов закрыта. |
| disabled | Управление ПК выключено, все переключаемые модули Olympus отключены. Проверяется фактический набор отключённых модулей после перезагрузки. |
| darkDraft | Видимое окно с фокусом в поле ввода черновика в ночном Olympus. Проверяются четыре работающие анимации после движения мыши и их состояние после 16 с без ввода. За следующие 30 с измеряется CPU всего дерева и процесса GPU в процентах одного ядра. Строгий smoke macOS сохраняет аналогичный замер кандидата в `theme/idle-cpu.json`. |
| Оба режима простоя | Private bytes, working set, CPU в процентах одного ядра и число процессов для main, renderer, сервера, хоста Olympus и всего дерева, включая помощников. Сырые файлы содержат имена образов. После 30 с стабилизации измеряются ещё 45 с. Допуск для добавочного постоянного процесса равен нулю. |
| Claude и Codex | Штатный адаптер запускает закреплённый Windows CLI в пустом профиле. Локальный HTTP-сервер удерживает первый запрос к модели. За 12 с измеряется дерево одного CLI вместе с помощниками. Для Codex это первый тред с общим app-server. Личные плагины и удалённая генерация в сценарий не входят. |
| UI | Два подготовленных треда, 300 строк сайдбара, 0/8/16 стримящих ACP-моков. p50 первого кадра и готовности, p95 ввода, FPS ленты под нагрузкой на проверенном пути колеса длиной 1 765 пикселей. Стенд проверяет доставку и отображение ответов. |
| Хранилище | 8 моков × 80 абзацев, одна версия Chromium headless shell на всю пару. Разность размеров SQLite + WAL + SHM и трейсов с учётом ротаций в КиБ. Окно checkpoint даёт заметный разброс физического размера. |

Отправная точка для абсолютных порогов интерфейса — [последний опубликованный парный замер UI](perf-ui.md), для диска — [серия с 8 агентами](perf-quick-wins.md) и [разброс WAL](perf-resources-2.md). Для новых сценариев простоя и чистых нативных CLI эталон измеряется заново на том же раннере. Лимиты изменения private memory, CPU и числа процессов указаны в JSON. Для private, WS, CPU и числа процессов дополнительно действуют зафиксированные абсолютные потолки. В основу легли успешные замеры main в контрольной паре и на второй Windows VM. Артефакты guard-main и guard-feature-artifacts дают девять запусков main для обычного простоя и агентов и два успешных для отключённых модулей. Для CPU отключённого состояния учтён также диапазон обычного простоя. [Калибровочный прогон](https://github.com/Zulut30/Chronos/actions/runs/45648111151).

Первоначальный стенд с 14 нажатиями давал максимум вместо устойчивой оценки p95. В контрольной паре с 16 агентами получено 31,9 и 50,7 мс. Текущий стенд измеряет 40 нажатий на запуск, допускает 20 мс парной разницы и проверяет абсолютный предел. На ранней ветке управления ПК (bc9ce41302) исходники приложения совпадали с main, однако попадание короткого всплеска в 12-секундное окно давало 0,13 → 2,21% CPU сервера. Для простоя увеличены время стабилизации и длина самого замера с сохранением парного допуска CPU. Старые значения FPS относятся к исходному жесту. Точность и применимость к конкретному профилю зависят от набора MCP и активности моделей.

На контрольном SHA `45c3dbfe14` все 61 проверки прошли. В шести запусках main рост SQLite с WAL и SHM составил 3 739–11 846 КиБ, медиана 6 789,1 КиБ. Трейсы выросли на 286–322 КиБ, медиана 293,3 КиБ. Простой занял 8 процессов в обеих половинах пары. [Контрольная пара и полная таблица](https://github.com/Zulut30/Chronos/actions/runs/45652389790/job/139340703727).

После замера интерфейса стенд выбирает конкретную карточку с заглушкой за пределами видимой области, прокручивает саму панель шагами до 80% видимой высоты, ждёт появления содержания в той же карточке, проверяет фокус и открывает тред клавишей Enter. При каждом шаге измеряется текущее положение карточки. При однократном scrollIntoView цель на контрольном main оказалась на высоте 1 613 px при нижней границе панели 856 px. Ограниченный шаг учитывает изменение высоты списка при подгрузке карточек. [Диагностический прогон](https://github.com/Zulut30/Chronos/actions/runs/45662215772).
