# Выгрузка простаивающих тредов Claude и ACP

## Как работает

В сборке 5209 драйверы в `apps/server/src/provider/Drivers` выбирают бинарники и создают адаптеры. Живые сессии принадлежат `orchestration-v2/ProviderSessionManager`. У Claude открытие сессии создаёт область ресурсов, а SDK запускает CLI при первом ходе и переиспользует его между ходами. Старая политика закрывала сессии с native resume через 2 минуты, остальные через 30. Обращения к живому runtime и события провайдера продлевали таймер. Фоновая работа могла удерживать сессию до 4 часов с последнего прогресса. Возраст PID из замера машины сам по себе не показывает, какой именно сигнал удерживал процесс.

В Chronos настройка **Провайдеры → Дополнительно → Выгружать Claude и ACP при простое** действует на сервер выбранного окружения. По умолчанию это 10 минут. Значение 0 выключает автоматическую выгрузку Claude и поддерживающих возобновление ACP-сессий, а смена числа действует и на уже открытые треды. Старый сервер не присылает это поле, поэтому клиент скрывает его. Режим сжатия контекста Claude и его порог токенов настраиваются отдельно.

Один серверный таймер раз в 30 секунд проверяет сроки живых сессий. Закрытие начинается после заданного интервала и ближайшей проверки. Чтение дескриптора сессии не продлевает этот срок. Для каждого кандидата Chronos проверяет незавершённые и отложенные ходы, запросы разрешений и пользовательского ввода, команды, зарегистрированные фоновые задачи, сабагентов, ожидающую доставку результатов и открытые PTY треда. Адаптер дополнительно проверяет собственный активный ход, диалоги, запланированные пробуждения, отложенные сообщения SDK и наличие диалога в нативном транскрипте. Интерактивная карточка MCP тоже удерживает живой транспорт для действий пользователя. Начатый вход в MCP (после нажатия «Войти») удерживает CLI до завершения входа, но не дольше 15 минут. Одна лишь неотвеченная карточка «нужен вход» процесс не держит: у профиля с постоянно неподключёнными MCP иначе выгрузка не срабатывала бы никогда. После выгрузки кнопка «Войти» просит сначала отправить сообщение, которое снова поднимет сессию. Защита действует, пока условие сохраняется. После срабатывания защиты срок отсчитывается снова.

До первого сообщения CLI сервер снимает дерево его процессов. При просроченном таймере в дереве могут оставаться сам CLI и стартовые помощники, включая MCP. Появление дополнительного живого процесса, смена времени рождения PID или недоступный снимок оставляют CLI в памяти. Windows использует PID, ParentProcessId и CreationDate из CIM, Unix использует `ps` и учитывает также группы процессов, ранее замеченные дочерние задания и членов systemd scope после смены родителя. Аргументы процессов и содержимое диалога в эти проверки и журналы не попадают. Поздно стартовавший MCP тоже может удержать сессию. Проверка стоит одного снимка при холодном запуске и одного при попытке выгрузки подходящего кандидата.

Закрытие и следующее открытие сериализованы по ID сессии. Перед удалением проверяются объект runtime, поколение активности и актуальная настройка под разрешением на запись запросов. Штатный release завершает подписки, закрывает scope и вызывает SDK Query.close. На Windows обработчик принадлежащего CLI умеет завершать его дерево. Финализатор ждёт выхода PID до 5 секунд, превышение этого срока пишет отдельное событие `chronos.claude.exit-still-pending`. В проекции остаются история, идентификатор нативного треда и статус сессии `stopped` с пустым lastError. Следующий ход, включая запрошенную компактизацию, проходит через обычный `open → resumeThread`; SDK открывает тот же Claude session ID. Ожидающий подтверждения диалог сохраняет живой процесс. События `chronos.claude.idle-unloaded` и `chronos.claude.native-resumed` можно сопоставить по providerSessionId. Второе также относится к другим нативным возобновлениям.

### Нехватка памяти Windows

Сервер проверяет доступную физическую память Windows в том же цикле. Порог по умолчанию — меньшее из 10% физической ОЗУ и 2048 МиБ. Для треда без открытой подписки просмотра срок сокращается до одной минуты. Все проверки процесса, транскрипта, терминалов и незавершённой работы продолжают действовать. Под блокировкой сервер повторно проверяет доступную память и зрителей во всех подключённых клиентах. Обычный срок действует и для открытого треда.

Переменная окружения сервера `CHRONOS_CLAUDE_LOW_MEMORY_MIB` задаёт порог в МиБ. Значение 0 выключает ускоренную выгрузку. Настройка общего срока 0 выключает обе формы выгрузки. На других ОС действует обычный срок.

## Провайдеры

| Провайдер | Поведение |
| --- | --- |
| Claude Agent SDK | Настраиваемое закрытие процесса и его сессии. У каждого треда собственный CLI. |
| Codex | Общий app-server. Менеджер разгружает отдельный нативный тред через `thread/unsubscribe` и ждёт `thread/closed`. Аргументы T3 по умолчанию задают `thread_unload_delay_secs=0`; явный аргумент пользователя имеет приоритет. Процесс может обслуживать другие треды. |
| Antigravity и другие ACP | После согласования `session/load` или `session/resume` применяется тот же настраиваемый таймер и проверка дерева транспорта. Дополнительные причины оставить ACP живым — открытый клиентский терминал, недоставленное решение пользователя, очередь продолжения и нативная фоновая работа. При отсутствии поддержки нативного возобновления сохраняется политика апстрима с передачей контекста. При закрытии или архивировании последнего треда его эксклюзивная сессия освобождает scope агента и stdio-моста. |
| OpenCode | Использует собственный серверный адаптер. У v2 общий runtime, отдельная выгрузка тредов и проверки фоновой работы. Отдельный срок Claude к нему не применяется. |

Встроенный WSL-бэкенд Windows-пакета поставляется как официальный Linux CLI апстрима. Для проверки изменения нужен локальный сервер Chronos или удалённый сервер именно этой ветки.

## Как проверить вручную на Windows

1. В тестовом профиле Chronos выбрать локальное окружение и установить 1 минуту. Открыть два треда Claude. В первом попросить запомнить случайный маркер, дождаться ответа и записать PID CLI и его дочерние процессы. Для второго запустить ход или оставить диалог согласования открытым.
2. Через 60–90 секунд проверить событие выгрузки первого треда, исчезновение его PID и стартовых MCP. Проверить, что второй CLI ещё жив, и ответить на запрос из его окна.
3. В первом треде спросить маркер. Проверить один новый PID, тот же nativeThreadId, правильный ответ без повторной передачи маркера, прежнюю историю и отсутствие ошибки. Повторить с сообщением на границе таймера и убедиться, что ход стартовал один раз.
4. Повторить с открытым терминалом, активным дочерним процессом и фоновым сабагентом. Проверить, что они доживают до завершения. Закрыть терминал, дождаться окончания работы и следующего полного интервала. Установить 0 и убедиться, что ещё один простаивающий тред остаётся жив после интервала. Вернуть 10.
5. Сравнить сумму **Private Bytes** одного и того же дерева до выгрузки и после неё. Записать отдельно working set и задержку первого ответа после возобновления.

## Ожидаемая экономия и ограничения

В исходном замере Windows семь Claude CLI занимали примерно 715–916 МБ private memory каждый. Дерево stdio MCP добавляло порядка 500 МБ. Исчезновение одного такого дерева должно освободить около **1,2–1,4 ГБ private commit**; десяти сопоставимых деревьев — порядка **12–14 ГБ**. Это оценка по исходному замеру. Фактическое освобождение физической RAM зависит от резидентности страниц. Таймер помогает при чередовании работы и простоя. Пиковая память одновременно выполняющихся ходов остаётся отдельной величиной.

На этом Windows-ПК контрольный процесс и дочернее задание дали 1 → 3 → 1 процессов в снимке. После завершения задания PID и время создания совпали с исходным снимком. Мок-тесты проверяют политику, состояние проекции и идентификатор при возобновлении. Реальный выход claude.exe и всех MCP, сохранение контекста установленной версией SDK, вид поля в окне и задержка холодного запуска требуют проверки на desktop-сборке. Открытый PTY, неподтверждённая история, неизвестный процесс и ошибка чтения оставляют сессию живой. Изменённый или удалённый пользователем транскрипт после выгрузки обрабатывается обычным механизмом восстановления T3.
