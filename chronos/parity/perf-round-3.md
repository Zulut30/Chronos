# Третий раунд оптимизации Chronos

База третьего раунда — `5f3cfe29e7`. С ней сравнивались изменения сайдбара, холодного запуска и сервера. Для разбора прежней регрессии прокрутки в контрольную серию включили также пакет до переноса T3 #42582 и пакет с одним этим переносом. Все сравниваемые пакеты внутри каждой серии запускались на одной Windows VM.

## Итог раунда

В коде приложения оставлено чтение `spanId` и `traceId` по запросу (`503656e494`). Самые устойчивые изменения — уменьшение загрузки сервера с 16 агентами и более ранняя готовность кнопки на первом экране чистого профиля. Для каждого сценария провели две независимые серии на Windows. В каждой ячейке указаны медианы трёх пар на одной VM.

| Метрика | Первая VM, база → итог | Повтор на другой VM, база → итог |
|---|---:|---:|
| CPU сервера, 16 агентов, % одного ядра | 51,66 → 43,70 | 35,94 → 33,42 |
| RSS сервера, 16 агентов, МиБ | 433,86 → 437,87 | 438,51 → 436,91 |
| Готовность первого экрана, мс | 4803 → 4484 | 4910 → 4467 |
| Первый показ содержимого, мс | 1129 → 1251 | 1305 → 1286 |
| RSS renderer, 1002 треда и 16 агентов, МиБ | 1042 → 1029 | 1112 → 1168 |

В итоговой серии с одинаковым путём колеса исходный пакет до #42582 и итог дали 53,06 → 53,17 FPS при 8 агентах и 52,77 → 53,27 FPS при 16. Первый кадр переключения сохранил выигрыш 47% и 45% соответственно. Медианы базы третьего раунда на этой же VM были на 0,60 и 0,40 FPS выше итоговых. Абсолютные 57,0 и 55,2 FPS в контролируемой серии не достигнуты. [18 итоговых замеров](https://github.com/Zulut30/Chronos/actions/runs/45666662195)

### Отвергнутые эксперименты

- Создание JSX карточки при показе (`fb46978d1d`) снизило FPS в исходном парном замере и увеличило RSS во всех трёх парах с 16 агентами.
- Динамический импорт палитры и поиска по настройкам (`01595e1275`) увеличил медиану времени до готовности первого экрана на 504 мс.
- Буфер SQLite только для многочастных ответов (`20049ee42a`) увеличил медианы CPU и RSS при обеих нагрузках.
- Подключение подробных подсказок только возле видимой области (`269a98b2ed`) дало разнонаправленные результаты для памяти и снизило медиану FPS при 8 и 16 агентах.

Второй пакет дополнительно откладывает создание DOM скрытых карточек. [Исходные измерения](https://github.com/Zulut30/Chronos/actions/runs/45613980606)

| Моки | Без отложенных карточек | С отложенными карточками | Пройдено пикселей |
|---:|---:|---:|---:|
| 8 | 54,94 | 56,82 | 575 → 5021 |
| 16 | 55,00 | 55,61 | 575 → 575 |

Эта серия не воспроизводит падение при добавлении карточек. При восьми агентах существенно различалась даже дистанция прокрутки. Единственная пара не устанавливает причинность и не обосновывает откат сайдбара.

В той паре, из которой получены целевые 57,0 и 55,2 FPS, различалась нагрузка самой прокрутки. Старое поле `distance` содержит модуль разности конечной и начальной координат после смены направления колеса. При восьми агентах смещение составило **5021 → 575 px**, при шестнадцати — **575 → 5021 px**. Сумма команд колеса в каждом случае равна +575 px. По исходным данным нельзя отделить работу приложения под стримом от перемещения виртуального списка. [Исходная пара](https://github.com/Zulut30/Chronos/actions/runs/45615943201)

## Память renderer при 1000+ тредах и 16 агентах

Стенд подготовил 1000 обычных тредов и два чата с историей, затем запустил 16 моков. Снимок RSS сделан до завершения всех ответов, после переключений и набора текста в активном чате. В каждом запуске проверены тексты 18 историй, стоимость и итоговая скорость всех 16 агентов. Сумма RSS относится только к renderer-процессам этого экземпляра. Показание JS heap зависит от момента сборки мусора.

| Кандидат | RSS, три пары, МиБ | Медиана RSS, МиБ | Медиана JS heap, МиБ |
|---|---|---:|---:|
| Создавать JSX карточки при показе | 1032 → 1169 · 1041 → 1070 · 1073 → 1112 | 1041 → 1112 | 442 → 385 |
| Загружать содержимое палитры при открытии | 1151 → 1142 · 1001 → 1124 · 1028 → 1021 | 1028 → 1124 | 396 → 394 |
| Подключать подробную подсказку возле видимой области | 1016 → 1118 · 1061 → 1043 · 1056 → 1013 | 1056 → 1043 | 438 → 431 |
| Читать идентификаторы трассировки по запросу | 1072 → 1016 · 1023 → 1029 · 1042 → 1079 | 1042 → 1029 | 435 → 438 |

У отложенного JSX RSS вырос во всех трёх парах. Выигрыш 137 МиБ в одиночном замере без агентов не перенёсся на совместную нагрузку. [Три пары на одной Windows VM](https://github.com/Zulut30/Chronos/actions/runs/45644086216)

Для палитры выигрыш двух пар составил по 8 МиБ, в оставшейся паре RSS вырос на 123 МиБ. Оснований сохранять этот кандидат ради памяти нет. [Замер палитры под совместной нагрузкой](https://github.com/Zulut30/Chronos/actions/runs/45644259253)

В эксперименте `269a98b2ed` подробная подсказка треда подключалась при приближении строки к видимой области сайдбара. Стенд после замера наводил мышь на строку и проверял заголовок открытой подсказки. Во всех шести запусках первой серии подтвердились 16 одновременно отвечающих агентов во время снимка, 16 подробных подписок и успешное открытие подсказки. В одной паре затраты памяти выросли на 102 МиБ, в двух снизились на 18 и 44 МиБ. [Первая серия подсказок](https://github.com/Zulut30/Chronos/actions/runs/45649719115)

На второй VM две полные пары дали 1045 → 1155 и 1160 → 1122 МиБ. В третьей у кандидата истекло время ожидания раскрытия дальней карточки сайдбара. Для неполной пары выигрыш не вычислялся. Снижение памяти оказалось невоспроизводимым, а медианы FPS в серии с колесом уступили базе в обеих нагрузках. Изменение снято коммитом `06bdf934c1`. [Повтор совместной нагрузки](https://github.com/Zulut30/Chronos/actions/runs/45653270641)

У изменения трассировки renderer занимал на 56 МиБ меньше в первой паре и на 5 и 38 МиБ больше в остальных. Медиана первого кадра переключения при 1002 тредах с 16 агентами выросла с 609 до 624 мс, первый кадр был позже во всех трёх парах. [Проверка трассировки на большом сайдбаре](https://github.com/Zulut30/Chronos/actions/runs/45657535826)

В повторе с обратным порядком RSS базы и кандидата составил 1148 → 1170, 1112 → 1128 и 1077 → 1168 МиБ. Медианы — 1112 → 1168 МиБ. Первый кадр, напротив, стал быстрее во всех трёх парах, с 480 до 474 мс по медиане. Итого renderer занимал больше памяти в пяти из шести пар. Доказанного выигрыша памяти при 1002 тредах и 16 одновременно отвечающих агентах нет. [Повтор большого сайдбара](https://github.com/Zulut30/Chronos/actions/runs/45659534633)

## Холодный запуск Electron

У настроек и страницы «Расход» включено автоматическое разделение маршрутов TanStack Router. Каталог поиска по настройкам дополнительно импортируется палитрой команд из корня приложения. Эксперимент `01595e1275` перенёс содержимое палитры и каталога в динамический импорт внутри всплывающей панели. Кнопки, горячие клавиши и контейнер фокуса подключались при старте как прежде. Браузерные тесты палитры и поиска прошли. Доска задач открывается из сайдбара кодом Olympus, Студия загружает интерфейс сервиса при открытии. Их точки входа покрывает функциональный smoke.

Три пары на одной Windows VM, каждый запуск — новый процесс и пустой профиль. Порядок пакетов во второй паре обратный. В обеих версиях готовность измерялась от запуска EXE до видимой активной кнопки первого экрана `/welcome`. Первый показ содержимого взят из Chromium Paint Timing. Эти числа относятся к первому запуску профиля. [Артефакты и браузерные проверки](https://github.com/Zulut30/Chronos/actions/runs/45644198587)

## Сервер при 8 и 16 агентах

Эксперимент `20049ee42a` изменял обмен с SQLite worker. Буфер подтверждения создавался только для результата из нескольких порций. Один короткий запрос обходился без выделения `SharedArrayBuffer`. Отдельная функциональная проверка вернула 32 770 строк по порядку с двумя подтверждениями, следующий короткий запрос вернул одну строку. Прошли тесты SQLite для читателя и писателя. [Проверки кода](https://github.com/Zulut30/Chronos/actions/runs/45645509200)

По три пары AB, BA, AB на одной Windows VM. Каждый агент отправлял 80 абзацев, клиент держал подробную подписку на каждый тред. CPU измерен по процессорному времени всего серверного процесса в процентах одного ядра. RSS снят в конце рабочего интервала. Все 11 520 маркеров и конечные тексты 144 ответов проверены в обеих сборках суммарно (`(8 + 16) × 3 × 2` ответа). [Результаты сервера](https://github.com/Zulut30/Chronos/actions/runs/45648793113)

| Агенты | CPU, % одного ядра | RSS сервера, МиБ | Доставка p95, мс |
|---:|---:|---:|---:|
| 8 | 29,15 → 32,84 | 396,08 → 399,49 | 515 → 514 |
| 16 | 41,55 → 42,30 | 437,93 → 439,78 | 521 → 521 |

Сокращение выделений не снизило медианы CPU и RSS. Изменение снято коммитом `4a5bf26afc`. До полной пары были два инфраструктурных сбоя — HTTP 503 у хранилища артефактов и отсутствие CDP у предустановленного Chrome runner. Стенд повторяет временные ошибки загрузки и для серверной серии устанавливает один Chromium Headless Shell для обоих пакетов. Эти попытки не включены в таблицу.

Эксперимент `503656e494` изменил момент чтения идентификаторов локальной трассировки. Effect 4.1.5 генерирует идентификатор при первом чтении, однако обёртка Chronos запрашивала его сразу для каждого span. Кандидат запрашивает идентификатор при экспорте, при чтении клиентом или при построении связи с родителем. Частота отбора обычных успешных операций осталась 1/16. Ошибки и предупреждения по-прежнему попадают в файл. Проверки родительских связей, маскирования секретов в URL и сохранения поздних ошибок прошли в CI. - В `20-speed.js` использовать разобранный кадр от общего обработчика `05-oly-core.js`.
