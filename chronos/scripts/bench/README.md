# Нагрузка на упакованный Chronos под Windows

Нужны Node 24+, Git и Chromium. Стенд запускает сервер из `resources/server.asar` через лежащий рядом `Chronos.exe` в режиме Node. Подойдёт установленный Chronos или содержимое `app-64.7z` из Windows-артефакта CI. Указывать нужно каталог с `Chronos.exe`. Chromium открывает веб-клиент из проверяемой сборки.

```powershell
# Укажите путь к имеющемуся Chrome for Testing / chrome-headless-shell для обеих сборок.
$env:BENCH_CHROME = 'C:\tools\chrome-headless-shell\chrome-headless-shell.exe'
node --test chronos/scripts/bench/agent.test.mjs
node chronos/scripts/bench/run.mjs 'C:\tools\Chronos-base' 4 "$env:TEMP\base-4.json"
node chronos/scripts/bench/run.mjs 'C:\tools\Chronos-candidate' 4 "$env:TEMP\candidate-4.json"
```

Аргументы после файла результата задают число чанков и паузу в миллисекундах. По умолчанию каждый агент отправляет 80 абзацев с паузой 125 мс. У каждого абзаца есть идентификатор треда, порядковый номер и время отправки. Для диагностической пары с полным локальным трейсом установите `$env:BENCH_TRACE_LEVEL = 'Info'` и уберите переменную перед серией с обычным дефолтом. Для N = 4, 8 и 16 и каждого повтора укажите своё имя JSON. Запускайте серии последовательно.

Стенд создаёт временный профиль браузера, пустой Git-проект, `CHRONOS_HOME`, `T3CODE_HOME` и отдельные каталоги провайдеров. В окружение дочерних процессов передаются только системные переменные из разрешённого списка. Вызовы модели заменяет локальный ACP-процесс. Заголовок треда задан, провайдеры платной генерации отключены. Браузеру разрешён прямой доступ лишь к порту своего сервера, порты сервисов Olympus дополнительно блокируются в CDP.

Драйвер создаёт N тредов через штатный RPC и подписывается на N потоков подробностей. В отдельном Chromium открыт первый тред. Измерение начинается после синхронизации всех подписок, готовности всех агентов и появления исходного запроса в DOM. Успех требует завершения всех запусков, получения каждого маркера нужной подпиской, совпадения финального текста каждого ответа с выводом мока и присутствия последнего маркера открытого треда в DOM. Задержка события измеряется от отправки моком до первого получения маркера WS-драйвером. Она включает буферизацию текста.

CPU приведён в процентах одного ядра по приращению процессорного времени. RSS снимается в конце интервала. Для Chromium учитываются процессы типа renderer из приватной CDP-сессии, их набор должен совпасть в начале и конце. Для сервера встроенный измеритель event loop считает p95 по `monitorEventLoopDelay` с разрешением 10 мс и вычитает эти 10 мс. Рост БД включает файлы SQLite, WAL и SHM. Байты трейсов включают ротации; последней буферизованной записи даётся 1,3 с на сброс. Время холодного старта, память моков и процессы GPU в метрики не входят.

## Замер интерфейса

Для проверки веб-клиента распакуйте Windows-артефакт нужного SHA. Из корня репозитория запустите:

```powershell
node chronos/scripts/bench/ui.mjs web C:/tools/Chronos 8 "$env:TEMP/ui-web-8.json"
```

Значения нагрузки — 0, 8 или 16. Каждый стримящий агент отправляет 480 фрагментов кода с паузой 85 мс. Для прокрутки стенд заранее создаёт 300 обычных тредов. Переменная `BENCH_UI_ROWS` принимает целые значения от 300 до 1000. Веб-режим использует тот же изолированный сервер, профиль Chromium и блокировку сети, что и основной стенд. `BENCH_UI_TRACE=1` сохраняет Chromium trace в `<файл результата>.trace.json.gz`. `BENCH_UI_CADENCE=1` дополнительно измеряет промежутки между изменениями одного длинного ответа в RPC. Используйте эти режимы в отдельных диагностических прогонах.

Для Electron запустите `chronos-checks.yml` с параметром `ui_builds` — списком числовых ID desktop-сборок через запятую. Workflow скачивает артефакты на одну одноразовую Windows VM и прогоняет пакеты последовательно. В каждом запуске создаются отдельные профили Electron, Chronos, T3 и провайдеров. Штатные сервисы Olympus запускает сам пакет на этой VM. Результаты, скриншоты и полный smoke-отчёт лежат в артефакте `packaged-ui`. Для локального Windows-ПК с установленным приложением используйте режим `web`.

Время переключения отсчитывается от вызова обработчика строки до первого rAF с адресом и содержимым целевого треда. Затем стенд дожидается конечного маркера и редактируемого композера. Ввод проходит через CDP Input, прокрутка — через события колеса. FPS показывает частоту rAF за этот интервал. RSS включает renderer-процессы отдельного экземпляра. Перед записью результата стенд сравнивает серверный текст каждого ответа с выводом мока и проверяет финальный маркер в DOM.
